# Skydimo UI 发布门禁需求与开发规划

日期：2026-10-01。状态：规划；S0 与部分 S1 已在工作区实施，尚非完整发布门禁。评估基线：`6fc3dd0c62a0568c0bf244c8d1a002a1a144049f`。

本规划优先覆盖 Simple 与 OEM，Advanced 分阶段纳入。建议第一阶段以 Windows x64 为执行平台，复用现有 Playwright、原生 WebView2 审计、安装包校验和 soak 运行器，建立统一的覆盖清单与发布判定。平台范围是本规划建议；其他已对外支持的平台仍须提供自己的发布证据。

这次评估读取了当前源码、测试和 workflow，并核对了官方工具文档；没有执行安装器、实机测试或长时间测试，也没有读取实际 Gitea 运行记录。因此，“已实现”表示代码中存在相应能力，“已接线”表示 workflow 调用存在，均不等于当前候选版本已经通过。

## 1 当前基础与重新评估

现有体系值得继续建设。主要问题是测试覆盖、产物身份和发布判定尚未统一，部分关键路径还会跳过。旧的 [Simple 发布门禁文档](../docs/architecture/simple-release-gate.md) 最近复核于 2026-07-28，其中部分缺口已被后续代码关闭，应保留历史背景并按当前证据重新核对。

| 范围 | 当前可核实的事实 | 还不能证明的内容 |
| --- | --- | --- |
| 浏览器 E2E | `playwright.config.ts` 有 Simple、Advanced project；真实 Core、真实 WS、虚拟 UDP 设备；Windows CI 已调用 `npm run e2e` | 最终安装包与 Tauri 壳完整交互；OEM 六品牌覆盖；实际 CI 运行通过 |
| Simple 主流程 | 有启动、引导、扫描、电源、设置等用例；已有 transport 单元测试 | `effects.spec.ts` 两条 Simple 灯效用例显式 skip；设置用例还会因入口不存在而 skip |
| 灯效断言 | 部分用例读取虚拟设备实际输出帧 | 切换前后帧不同可能只是同一动态灯效随时间变化，仍需独立核对 Core 的 effect ID、参数和目标 |
| 原生桌面审计 | `windows-native-ui-audit.mjs` 可启动五个桌面壳，检查品牌、标题、React 根、溢出、页面错误与清理 | 对象是隔离未签名测试包；未覆盖 MageeLife、VIB；尚未在已检查的 workflow 中发现调用 |

| 发布安装冒烟 | Windows release workflow 已传入 `-InstallForSmoke`；脚本安装、校验、启动包内 Core、卸载并检查主程序移除 | 跨版本升级、用户数据迁移、桌面生命周期、原生弹窗、完整卸载残留与回退 |
| AARGB2 soak | 有真实 UI 动作、独立 Core 断言、Seed、动作重放、checkpoint 恢复、覆盖缺口与失败分类 | 其他 OEM 适配、资源趋势采样、统一磁盘配额、全局墙钟上限、完整原生功能与光学验证 |
| 发布汇总 | 已有 release plan、文件哈希、品牌和插件清单校验 | 本次未发现把确定性 UI、原生 UI、升级恢复、硬件与 soak 全部绑定到一个候选版本的统一准入判定 |

现阶段应先补齐可判定的关键路径，再扩展覆盖广度。单测数量、截图数量、页面能打开和随机点击次数，均不单独作为发布合格依据。

## 2 范围与产品矩阵

“全面”定义为：发布清单声明支持的产品、能力、平台和设备，每项关键用户需求都有正常、失败和恢复路径，有执行证据和负责角色。无需穷举全部参数组合，但不得遗漏高风险状态和品牌差异。

| 产品或布局 | 必测内容 | 覆盖安排 |
| --- | --- | --- |
| Skydimo Simple | 标准设备流程、设置、首次引导；按实际开关覆盖会员、反馈和高级入口 | 第一阶段完整核心流程 |
| AARGB、MageeLife、VIB | 共用 OEM 操作流程，各自身份、资源、设备能力、入口与安装配置 | 共用交互适配器；每个出货品牌独立身份与能力验收 |
| AARGB2 | 单屏工作区、批量目标、在线预设、多色、来源、通知；禁止联动策略 | 第一阶段独立适配器与核心专项 |
| Apex | 三栏布局、设备选择、来源和模式控制、灯珠边界、品牌资源 | 第一阶段独立适配器与核心专项 |
| Advanced | 初期保留现有回归与壳启动；后续覆盖 Scope、布局、矩阵、插件等 | 后续深度扩展；凡实际随安装包交付或可达的关键路径，仍需最低阻断检查 |

品牌清单从 `branding/*.json` 与 release plan 读取，本次有 `skydimo/aargb/aargb2/apex/mageelife/vib` 六个配置。正式门禁按当次发布清单选择，不能把未测品牌标为通过。

品牌配置是预期值的一部分，仍需独立的产品能力清单。不能仅根据界面实际显示的按钮反推“应该有何功能”，否则遗漏入口会被误认为不适用。`manufacturerAllowlist` 只有在 enforcement 启用时才限制设备；测试必须核对实际策略，不能见到列表就假设过滤生效。

## 4 分层执行与产物一致性

| 层级 | 被测对象 | 核心用途 | 不能替代的证据 |
| --- | --- | --- | --- |
| L0 组件与协议 | 组件、transport、DTO、受控 Mock Core | 穷举错误、乱序、能力变化、文案和控件状态 | 真实 Core、系统集成、物理输出 |
| L1 确定性浏览器 E2E | 当前提交构建的 UI + 测试 Core + 虚拟设备 | 高频核心操作、Core 权威状态、输出帧、重启持久化 | Tauri、最终二进制、真实 HID/串口 |
| L2 原生桌面 E2E | 已构建/已安装 Tauri + WebView2 + 包内 Core | 壳启动、窗口、托盘、WebView 行为、原生设置和恢复 | 硬件特性、安装升级全流程 |
| L3 交付验收 | 实际签名安装包与干净 VM | 安装、升级、卸载、资源/签名、用户数据迁移 | 灯光物理行为和长期设备稳定性 |
| L4 硬件与 soak | 最终安装包 + 专用设备/电源/Hub | 插拔、掉电、来源、长期资源趋势、实际灯光 | 未声明的设备/固件/平台组合 |

### 4.1 测试构建与发布构建分别记账

现有 E2E Core 显式启用 `virtual-test-device`，原生审计使用隔离未签名包；这些产物与最终签名安装包不是同一组字节。保留它们作为快速回归能力，不应为了获得形式上的一致性把测试后门带入正式产品。

每个候选版本建立两类证据：源码回归证据绑定产品 SHA、锁文件和测试构建配置；交付证据绑定最终安装包、包内 UI/Core/插件、品牌快照和文件哈希。两者都必须满足，且报告明确列出二进制差异。

RC 在签名、打包完成后冻结哈希，L2/L3/L4 使用该候选包。测试后只能提升该产物，不重新编译、重签或替换资源；任何变化生成新候选并重新执行受影响门禁。测试构建上的故障注入结论不能代替最终包的启动、断连恢复、安装和硬件验收。

### 4.2 工具选择

Windows 继续采用现有 Playwright + WebView2 CDP 路线，先扩展 `windows-native-ui-audit.mjs` 的生命周期与证据能力，再抽出可复用 fixture。Playwright 官方支持通过进程环境变量开启 WebView2 调试并附加，也明确建议隔离用户数据目录。[官方说明](https://playwright.dev/docs/webview2)

在专用 Runner 中，仅对测试启动的进程临时启用 loopback CDP；不修改正式安装包默认设置。增加不启用调试环境变量的启动/退出检查，防止全部桌面证据依赖特殊启动条件。托盘、系统对话框、窗口状态与重启使用独立的 Windows 原生自动化适配器，不能把 `page.close()` 当成关窗策略测试。

macOS/Linux 作为后续平台适配。当前 Tauri 官方文档已介绍跨平台 `@wdio/tauri-service` 的 embedded 方案；直接使用 `tauri-driver` 仍主要覆盖 Windows/Linux。嵌入测试驱动需要不同构建时，继续分别记录测试版与最终包证据，不默认认为工具可直接控制原封不动的发行包。[Tauri 官方说明](https://v2.tauri.app/develop/tests/webdriver/)

### 4.3 执行时间与矩阵

下列时间为规划预算，须以 Runner 实测校准；不把当前完整 Rust 构建承诺为几分钟内结束。

| 触发点 | 范围 | 初始时间预算 | 判定用途 |
| --- | --- | --- | --- |
| PR | L0/L1；Simple 与三类 OEM 布局代表；受影响品牌身份/策略；共享模块修改扩大矩阵 | UI 测试部分 10 至 15 分钟，构建单独记录 | 阻断合并 |
| 主分支及 Nightly | 六品牌原生关键流程、配置恢复、安装升级、短 soak；完整身份矩阵 | 确定性部分 30 至 60 分钟，另加 1 至 2 小时 soak；按 VM 扩容 | 发现集成回归，生成候选资格证据 |
| RC | 当次全部出货品牌、支持平台、最终包升级与恢复、硬件资格矩阵、24 小时 soak | 至少 24 小时，加设备矩阵与排队时间 | 阻断稳定发布 |

低风险组合采用成对组合覆盖语言、主题、DPI、WebView2 版本；品牌身份、关键策略、受支持升级起点和高风险设备边界必须明确逐项覆盖。OEM 六品牌不意味着在一台机器上同时启动六个 Core。

## 5 测试基础设施开发需求

### 5.1 覆盖清单与测试判据

新增机器可读的发布测试清单，至少记录：需求 ID、场景 ID、严重度、品牌/profile、能力前提、平台、执行层、预期测试数量、负责角色、性能预算和必需证据。预期值来自产品契约及独立固定样例，避免完全从被测实现生成断言。

按布局建立 Simple、Classic OEM、AARGB2、Apex 交互适配器，共享 Core 连接、设备 fixture、证据和断言。优先使用角色和可访问名称，设备身份等必要位置增加稳定 `data-testid`，避免 CSS 类名、列表下标和固定坐标。

UI 用例必须通过真实控件发起用户动作。RPC 用于已标记的准备、故障注入和独立结果查询，不能在动作之后用 setter 补写期望值。输出断言采用静态颜色/已知图样等确定性样例；动画帧变化只能证明输出在动，不能单独证明模式切换成功。

### 5.2 Core 生命周期与隔离

现有 Core fixture 的 `stop()` 同时停止进程并删除配置，无法直接承载同目录重启验收。建议拆成 start、stop、restart、dispose；restart 保留配置并重新获取实际端口/token，dispose 在证据采集结束后清理。

继续使用独立 app ID，并显式隔离 `SKYDIMO_CONFIG_ROOT`、`SKYDIMO_LOG_DIR`、WebView 数据目录；单独变更 `APPDATA` 不能代表全部 Windows Known Folder API 已被重定向。最终包另在可回滚的专用用户/VM 中验证默认目录行为。

`127.0.0.1:38967` 是整机单实例约束。多个 workflow 需要共享 Runner 租约/互斥，不能只给各 workflow 设置不同 concurrency group。每个 Core Runner 单 worker，需要并行时增加 VM。预检占用时报告环境未就绪，不抢占现有 Core；只清理本次确认归属的进程。

### 5.3 虚拟设备与故障场景

复用现有 UDP/mDNS fixture，增加固定灯珠、允许离散值、多输出、同名不同身份、离线、帧采集和错误能力样例。注意当前 `--virtual-devices-only` 会禁用扩展运行时，因此扩展页和插件生命周期必须安排独立的受控测试层。

短期在专用 Windows Runner 运行 mDNS；Linux CI 后续选择主机网络或测试专用的确定性注入方式。所有注入扩展保持测试 feature 隔离。模拟设备不能替代串口、HID、驱动失败和固件行为验证。

在 L0/L1 注入响应延迟、拒绝、断连、事件遗漏/重复、落盘失败及“请求超时但操作最终成功”；L2 验证真实 Core 崩溃后的端口/token 变化；L4 使用 USB Hub/继电器执行物理故障。测试结束后验证状态恢复，不能只证明错误出现。

### 5.4 性能与长时间测试

扩展现有 soak，而不是另建随机点击工具。保留 Seed、显式动作序列、恢复归因、覆盖缺口和原始失败；新增不同产品适配、CPU/内存/句柄/线程/RPC 延迟采样、日志与磁盘总配额、独立墙钟上限。

现有 checkpoint 只在当前 Core 生命周期有效。Core 重启测试应使用专用持久配置 fixture，不能假设重启后还可用旧 checkpoint 恢复。真实设备的离线固件写入需要可读回、可恢复的单独契约，没有该能力的场景必须明确留作人工或实验室验收。

随机 soak 补充确定性场景。24 小时跑满但关键动作未覆盖、设备被隔离、恢复失败或资源采集缺失，都不能通过。

## 6 发布判定规则

### 6.1 严重度与结果语义

沿用项目严重度含义：P0 为配置破坏或主程序不可用；P1 为核心路径错误、状态失真、不可恢复；P2 为存在可接受绕行的非核心问题。P0/P1 在稳定版发布时必须清零。P2 豁免需记录具体场景、负责人、证据、影响和到期版本。

统一结果使用 `passed/failed/blocked/incomplete/interrupted/not_applicable`。测试失败与环境阻塞分别归因，但必需任务只有 `passed` 才满足门禁；预先声明的不适用项有独立清单，不计入通过率。崩溃、持续拒连、缺设备、少跑用例、清理失败、报告缺失均不能转成成功。

运行时找不到预期入口应失败。按品牌禁用的功能应验证入口确实不存在，并验证对应策略，不能复用“入口不存在就 skip”的宽泛逻辑。已知问题隔离仍记作覆盖缺口；关键路径不得通过 quarantine 获得发布资格。

重试用于收集证据，不把偶发失败抹去。阻断套件启用 Playwright `failOnFlakyTests` 或等价汇总判定；保留首次失败和重试结果，人工判断真实基础设施故障后启动新的完整运行。[官方配置](https://playwright.dev/docs/api/class-testconfig#test-config-fail-on-flaky-tests)

### 6.2 初始验收指标

以下为建议起点，并非本次实测结果。S0 阶段按支持机器、固件和平台建立基线，冻结版本化阈值；没有预算的必需性能项不能宣称已完成验收。

| 指标 | 建议初始标准 | 测量边界 |
| --- | --- | --- |
| 必需功能场景 | 全部执行且通过，未批准 skip 为 0，关键 flaky 为 0 | 需求清单逐项对账，不按总通过率稀释失败 |
| 普通启动 | 非迁移冷启动 30 秒内、热启动 10 秒内进入可交互状态 | 进程启动至 UI 可操作、Core 已认证；慢迁移独立预算且全程可退出 |
| 普通交互 | 成功 RPC 后 2 秒内 UI 收敛到 Core 值 | 本地电源/亮度/普通参数；硬件写入与复杂采集另定预算 |
| 连接恢复 | Core 可连接后 15 秒内完成认证、重订阅和权威快照恢复 | Core 自身重启时长另外计时；产品恢复策略须明确 |
| 物理恢复 | 每个支持 SKU/固件资格组合至少 100 轮，无未恢复失败 | 明确数据断开与硬掉电；恢复时限按控制器冻结；欠压需合适电源和规格边界 |
| RC soak | 连续有效测试 24 小时，必需动作/来源/设备覆盖完整，未恢复错误为 0 | 准备、暂停、恢复时间不计入有效时间；按设备/品牌记录覆盖 |
| 资源健康 | 预热后满足绝对资源上限和相对基线增长预算 | UI、WebView2、Core 分别采样，冻结斜率/峰值/句柄阈值；禁止只看首尾截图 |
| 数据与隔离 | 配置损坏、跨品牌/非目标误写、无法解释的丢失为 0 | 比对独立快照，重启后再次读取 |
| 视觉与可访问性 | 关键操作遮挡、无法键盘操作、未审核的关键基线差异为 0 | 固定字体/平台/DPI基线，动态灯效单独采样，不盲目全页截图比较 |

资源阈值应在固定参考机器上测量，不能用跨硬件的任意 CPU 百分比判断回归。颜色准确度也应按硬件校准能力定义容差，不能要求未经校准的相机像素精确相等。

### 6.3 汇总与发布联动

新增门禁汇总器，将现有报告映射到统一 schema；它不执行 UI 动作，只核对候选身份、覆盖和结果。检查同一候选的所有必需任务是否完成、报告是否有效、哈希是否一致、是否存在阻断失败以及不适用/豁免是否符合规则。

必需字段包括产品 SHA、测试 SHA、锁文件/构建配置、candidate/build ID、品牌/profile、安装包及包内文件哈希、插件清单、OS/WebView2/Node/Playwright 版本、设备 SKU/固件、场景 ID、执行层、起止时间、退出码和重试记录。测试源码变化需产生新的测试 SHA，不能复用旧报告。

报告来自受信 Runner，并作为受保护流水线的产物存储；单纯在 JSON 中填一个 hash 不证明结果可信。发布入口必须依赖汇总结果，通过后只提升冻结产物。稳定渠道延续现有规划中的人工批准意图；“发布脚本先建 draft 再自动公开”不等于人工批准门禁。

## 7 证据与可维护性

每次运行至少生成可机器读取的汇总 JSON、JUnit、覆盖矩阵和人工可读摘要。失败场景附截图、ARIA/DOM 摘要、脱敏的 UI/Core/安装日志、操作记录、Core 状态差异；硬件场景附帧或传感器证据，性能场景附时间序列。成功运行也保存最小完整证据，不能仅失败时上传报告。

原始 trace/HAR 可能包含浏览器 URL 中的 `token`、WS 认证内容和用户数据。普通 CI 分享脱敏报告；隔离测试的原始取证材料需限制权限与保留期，确认脱敏后才可公开。真实用户配置、checkpoint 全量内容和长期凭据不得进入通用报告。

为资源上限保留必要失败证据，明确截断标记；关键证据缺失导致 incomplete。过期豁免、未实现需求、跳过原因与责任人应能在一份报告中看到。

稳定性治理包含：固定依赖和运行环境、基于条件的等待、可重现 fixture、独立用例、精确错误分类、失败重放。对流程超时同时保留事件时间线，减少靠增加 `waitForTimeout` 隐藏竞态的做法。视觉基线更新需要审核，不自动把新截图当作正确答案。
